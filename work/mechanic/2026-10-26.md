# 2026-10-26 저장소 점검

> 라이터의 이번 주 산출물이 실제로는 완성됐지만 네트워크 장애로 GitHub에 올라가지 못한 채 로컬 전용 브랜치에 갇혀 있고, `mergeMemory` 펜스 필터 버그(#21)는 3주째 미수정 상태로 이번 주 메카닉 자신의 기억 파일까지 오염시켰다.

## 발견

### 1. quill의 2026-10-24 산출물이 GitHub에 전혀 올라가지 않았다 — 로컬 전용 브랜치에 갇힘

`~/Library/Logs/ai_crew/quill.log`를 보면 2026-10-24 09:00 근무는 **글 작성까지는 완전히 성공**했다(`work/quill/2026-10-24.md` 1889자, memory.md 갱신, 턴 1·61초). 그런데 그 직후 브랜치를 origin에 올리는 단계에서 DNS가 죽었다:

```
✓ ✍️ 라이터 근무 완료
  → work/quill/2026-10-24.md (1889자)
...
fatal: unable to access 'https://github.com/heekeunlee/ai_crew.git/': Could not resolve host: github.com
✗ 근무 실패
fatal: unable to access 'https://github.com/heekeunlee/ai_crew.git/': Could not resolve host: github.com
```

`git branch -a`로 확인한 결과 로컬에는 `quill/2026-10-24` 브랜치가 커밋 `f2cd3c5`("✍️ quill: 2026-10-24")와 함께 그대로 남아 있는데, `remotes/origin/`에는 이 브랜치가 없다(08-29·09-05·09-12·09-19·10-10 브랜치는 전부 origin에 있다 — 10-24만 빠져 있다). PR도 당연히 없다. 즉 **이번 주 글은 실제로 완성됐지만 아무도 못 보는 로컬 git 참조 하나로만 존재한다.**

더 문제인 것은 이 실패를 아무도 알 수 없게 되어 있다는 점이다. `scripts/local/work.sh:74`의 실패 알림은 `[ "$ISSUE" != "0" ]`일 때만, 즉 이슈로 지시받은 근무일 때만 동작한다. 정기 근무(`ISSUE=0`)인 이번 경우는 `139b2c0 "✍️ quill 근무 실패 — 상태 정리"`라는 커밋 메시지 한 줄 외에는 아무 기록도 남지 않는다. 메카닉도 평소엔 `work/quill/`·`agents/quill/memory.md`만 보고 "변경 없음"으로 지나갈 사안이라, 이번에 로그 파일을 직접 열어보지 않았으면 놓쳤을 것이다.

**위치**
- `~/Library/Logs/ai_crew/quill.log:120-134` (실제 실패 로그)
- `scripts/local/work.sh:137-148` (브랜치 생성·push·PR 생성 — 복구 로직 없음)
- `scripts/local/work.sh:66-84` (`failed()` 트랩 — `$ISSUE=0`이면 어떤 알림도 안 남김)
- 로컬 브랜치 `quill/2026-10-24` (커밋 `f2cd3c5`, origin에 없음)

**고치는 법**
- 당장: 이 기계에서 `git push -u origin quill/2026-10-24 && gh pr create --title "✍️ quill: 2026-10-24" --base main --head quill/2026-10-24 --body "..."`를 수동으로 실행해 이번 주 글을 복구한다. 다음 주 근무는 새 날짜로 새 브랜치를 만들 뿐 이 브랜치를 건드리지 않으므로 지금 처리해도 늦지 않다.
- `work.sh:147`의 `git push`와 148의 `gh pr create`를 짧은 재시도(예: 2~3회, 몇 초 간격)로 감싼다 — DNS 끊김처럼 수초 안에 풀리는 일시적 장애에 지금은 한 번 실패하면 바로 유실로 이어진다.
- `failed()`에서 `pull-request` 리뷰 방식인 에이전트가 **콘텐츠 커밋까지 끝낸 뒤** 실패했다면(`$BRANCH`에 커밋이 있는 경우), `$ISSUE` 값과 무관하게 `gh issue create`로 "브랜치 `$BRANCH`에 안 올라간 산출물이 있다"는 이슈를 만들도록 한다. 지금은 이슈로 지시받은 근무가 아니면 이런 유실이 커밋 로그 한 줄 뒤로 조용히 묻힌다.

### 2. mergeMemory 코드펜스 필터 버그(#21)가 3주째 미수정이고, 이번 주 메카닉 자신의 기억까지 오염시켰다

`scripts/lib/memory.mjs:12-22`는 09-14에 처음 지적된 그대로다 — 노트를 줄 단위로 쪼갠 뒤 `filter(Boolean)`으로 빈 줄만 버리고, 하이픈·날짜 없는 순수 펜스 줄(` ``` `)은 걸러내지 못한 채 `- ${today} ${l}` 꼴로 그대로 기억에 박힌다. `scripts/memory.test.mjs`에도 이 케이스에 대한 회귀 테스트가 여전히 없다.

이번 주 새로 확인된 것은 두 가지다.
- **메카닉 자신의 기억이 오염됐다.** `agents/mechanic/memory.md:9-10`에 `- 2026-10-19 \`\`\`` 가 두 줄 연달아 박혀 있다. 지난주(10-19) 보고서는 "#21 코드 그대로이나 새 오염 없음"이라고 적었는데, 바로 그날 메카닉 자신의 출력이 같은 버그에 걸려 자기 기억을 오염시킨 것이다. #21 본문은 `agents/curator/memory.md`만 언급하고 있어, 이번이 이 버그가 curator 밖으로 번진 첫 확인 사례다.
- **curator 쪽은 계속 재발 중이다.** `agents/curator/memory.md:10`(`- 2026-10-24 \`\`\``)과 `:15`(`- 2026-10-21 \`\`\``)에 새 오염이 더 생겼다. 09-19 오염(지금은 `:35` 근처)은 아직 안 밀려났지만, 09-08 오염은 30줄 상한에 밀려 이미 사라졌다 — 즉 고쳐진 게 아니라 늙은 오염이 잘려나가고 새 오염이 계속 채워지는 상태다.

**위치**
- `scripts/lib/memory.mjs:12-22` (근본 원인, 09-14 이후 그대로)
- `scripts/memory.test.mjs` (회귀 테스트 여전히 없음)
- `agents/mechanic/memory.md:9-10` (새로 확인된 자기 오염, 10-19)
- `agents/curator/memory.md:10`(10-24)·`:15`(10-21) (새 재발)

**고치는 법**
- `mergeMemory`의 라인 필터(`memory.mjs:16` 근처)에 순수 펜스 줄을 버리는 조건을 추가한다: `.filter((l) => !/^`{3,}$/.test(l))`.

- `agents/mechanic/memory.md:9-10`와 `agents/curator/memory.md`의 남은 오염 줄은 사람이 직접 지운다(메카닉은 쓰기 권한이 없다).
